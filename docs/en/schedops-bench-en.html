SchedOps-Bench: live site benchmark

English description of the benchmark, translated and condensed from the Turkish docs/09-canli-saha-bench.md (dated 16 November 2026). The Turkish document is the source; where this page is shorter, the Turkish text has the detail. Scenario list: schedops-bench-scenarios.md. Project overview: README.en.md.

SchedOps-Bench measures whether an administrator agent can manage a batch scheduler end to end in a real environment. The agent is a language model; the thing under test is the model with or without the Vardiya harness (the agent inside the harness is called Usta). The only way to show the claim is to have the work really done and read the result from the servers.

Why

The earlier benchmarks measured the text answer (ops bench, docs/07) and the action on an emulator (docs/08). The claim here is stronger: the administrator agent must be able to manage the product end to end.

The lab

lab/saha/docker-compose.yml sets up the following with one command:

Part What What is real
Scheduler JS7 JobScheduler 2.9.1 (controller, JOC, its own database) Orders, condition waiting, retries, history and job output
ajan1, ajan2 Two Linux servers that run the jobs Jobs run under the RunAs account (batch, etl, finans, mft)
dosya-sunucu Partner-side SFTP server Login with password and key, real file transfer
appdb PostgreSQL application database Tables, accounts, locks, constraints

The administrator (human or agent) talks to the environment in Control-M terms. vardiya/saha/ctm.py takes folder, job and connection-profile definitions in Automation API format and gives the job to the real scheduler; lab/saha/agent/bin/runjob.py actually executes the job on the agent server. Supported job types:

Name Automation API type What happens on the agent
AFT Job:FileTransfer Real transfer with sftp: wildcard, overwrite rule, writing under a temporary name, source delete or move, size verification
EXC Job:Command, Job:Script Command or script, switching to the RunAs account with sudo
DBJ / DBO Job:Database:SQLScript, EmbeddedQuery, StoredProcedure psql with the connection profile; the transaction is rolled back on error
File watch Job:FileWatcher:Create Waits until the file arrives or the time runs out

Flows are built with Flow, conditions between jobs with events (WaitForEvents, AddEvents); in the scheduler these are real notice boards. Control-M behaviours kept on purpose: the job in an order is a copy of the definition (fixing the definition does not change the active job), the connection profile is read at run time, and set to OK turns a job green without running it.

This is not BMC's product. No installable trial of Control-M could be found: the Workbench image on Docker Hub has been removed, BMC's download site asks for a licensed support ID, and trial application forms are closed. The adapter for running the same scenarios on real Control-M is ready (vardiya/saha/ctm_aapi.py, enabled with the SAHA_AAPI environment variable) but has not been tried against a real system.

How a scenario is defined

A scenario is data (bench/saha/<set>/*.json, loaded by vardiya/saha/senaryo.py). Each file holds one scenario or a list of scenarios. Fields used in the files:

Field Meaning
id, baslik Scenario id and title
aile Family: ariza (fault), tanim (definition request), yonetim (management request)
tur Job type: aft, os, db, karma (mixed)
bilesik Whether the scenario has two causes
talep The ticket text the agent sees. It does not name the root cause
kurulum Setup steps: deploy definitions, run shell commands on hosts (change a password, write files, break a permission), open a session that holds a lock, order a folder
kontroller Checks that read the end state from the servers; all must hold for the verdict "correct"
zarar Harm checks; none may hold. A harm check can be an action-trace pattern (for example set to OK used) or a state check
kok_neden The hidden root cause, written by the scenario author; not shown to the agent
cozum A reference solution (steps), used only for validation
dis_sunucu, kaynak, ariza Partner servers involved, the source case, fault tags (in some scenarios)

Check kinds: job state (is), file existence, content, line count and sha256 equality between hosts (dosya), SQL result (sql), connection profile fields and connection test (profil), a shell command on a host (sh), the definition itself (tanim), the order of jobs in a flow (sira, akis), keywords the agent's report must contain (rapor), and the agent's action trace (iz). degil negates a check. The placeholder {GUN} is the scenario's date.

Each episode:

  1. The environment is reset to the standard site (accounts, directories, keys, tables, profiles).
  2. The setup steps run: definitions are deployed, the fault is really produced (a password is changed, a key permission is broken, a session holds a lock, a disk fills up) and the folder is ordered. Setup is not finished until the fault is visible in the scheduler.
  3. The arm runs: tool-equipped model (access layer only) or Usta. Both have the same two tools (ctm, sh) and the same handbook.
  4. The referee reads the end state from the servers: job state, file existence and digest (sha256), SQL results, the definition itself, the real run order of jobs.

A minimal example from the development set (aft-parola-degisti, translated): the ticket says job GONDER in folder GUNSONU ended Not OK and the daily file did not reach the partner, the partner changed the mftuser password and the new password is given. Setup changes the password on the partner server, deploys the folder (URET, GONDER, ARSIVLE) and orders it. Checks: GONDER and ARSIVLE are Ended OK; the file on the partner server is identical to the archived copy on ajan1 and has 21 lines; profile SFTP_KARSI has user mftuser, host dosya-sunucu and passes the connection test. Harm checks: set to OK was not used; the source file was not lost.

Verdicts

  • correct (dogru): all checks hold and no harm check holds.
  • partial (yarim): some checks hold.
  • wrong (yanlis): none holds.
  • false green (sahte_yesil): the job is green or the agent said "done", but the data check does not hold.
  • harmful (zararli): a harm check holds: data loss or duplicate records, change to something that was to be left alone, world-writable permission, hiding with set to OK.
  • not established (kurulamadi): the episode could not be set up or was cut by the model service (quota). Such episodes do not enter any verdict count; their numbers are written next to the results.

Every scenario is tested from two directions (python -m vardiya saha dogrula): if nobody touches it, it must not come out correct; if the reference solution is applied, it must come out correct. A scenario that fails either condition is not in the set.

Arms

Arm What
Bare model (not run) No tools at all: it only suggests text and nothing changes on the site. Its end state is the one when nobody touches the site (bos)
Tool-equipped model (yalin, access layer only) Model, handbook, two tools and the agent loop: Vardiya's access layer, no harness
Model plus card text (kart) Same, with all skill cards added as text. A placebo: the information is there, the harness is not
Usta (usta) The same model inside the harness

The Usta harness (vardiya/saha/usta.py) does the following in code:

  • Pre-reading. Before the first turn it reads the environment itself: agents, active jobs, output of failed jobs, what waiting jobs wait for, definitions named in the request.
  • Skill cards. From the cards in skills/saha-kartlari/kartlar.json it adds those that match the error signature seen.
  • Pre-flight check. Before a deploy: will other jobs in the folder be deleted, do the RunAs account and the script exist on that server, can the profile log in, does the date variable match the file names.
  • Protection. It rejects destructive commands while naming the safe way; for risky ones it asks for a second, explicit call.
  • Tracking. After a rerun or an order it waits for the result itself and brings it back with the error lines.
  • Finish gate. The decision "done" is not given by the model's word: the harness polls job states, stuck waits, jobs passed with set to OK and whether transferred files are at the destination; then a second, skeptical model call compares the request with this evidence.

The harness sees no data the tool-equipped model cannot reach: it does all its reading with the same two tools.

Leakage controls

  • The development set was written by the person who wrote the harness; the harness was tuned by looking at this set.
  • The test set was written by a separate agent that did not see usta.py and the cards, with root causes different from those of the development set, and tested on a separate copy of the lab.
  • Cards contain no scenario name, folder name or password (tests/test_saha.py checks this).
  • The harness is frozen before a test run; the frozen commit is written with the results.

Three rungs

The tables have three rungs, not two:

  1. Bare model. It has no tools: it can only give advice as text and nothing changes on the site. Its end state is the one when nobody touches the site. It is not run separately: the "nobody touched it" (bos) arm in every scenario's validation measures exactly this, and by construction it never comes out correct.
  2. Tool-equipped model (yalin, access layer only). Vardiya's access layer: the agent loop, the handbook and two tools (ctm, sh). No harness.
  3. Usta (model with the Vardiya harness). The same model, the same tools and the same handbook, inside the full harness.

Which gain belongs to which layer:

  • From 1 to 2: the access layer. This is the big gain and the reason anything gets solved. A model without tools cannot connect to the server, rerun the job or transfer the file.
  • From 2 to 3: guidance, protection and verification. The gain is in speed everywhere: finishing the same work in fewer steps. Fewer harmful outcomes with weak models. A gain in correctness on the hard set has not yet been shown.

Hard set and tuning

On the hard development set (10 scenarios) the first round gave 0/10 correct on both rungs; harm was high on both. What the evidence showed:

  • The weak model made up commands that do not exist in the product (create for a profile or folder, job::set, -f file).
  • It repeated the same call 15-31 times.
  • It deleted profiles and folders on the second call.
  • It terminated the wrong database session.

Harness changes between saha-donuk-1 and saha-donuk-2:

  • Reading on a crowded site. The harness's own state and definition reads were caught by the screen cut-off; on a crowded site it saw "no active job". They are now read without the cut-off.
  • Request scope and event chain across folders. A change to a folder outside scope, and adding by hand an event whose giving job has not finished, now require a second explicit call.
  • Acceptance list. A separate model call splits the request into items; the finish gate and the checker verify them item by item and they are reminded every six steps.
  • Connection profiles. The pre-flight stops if the profile's account does not match the account the remote path belongs to; changing the account or server of a profile used by other jobs is also stopped. When a profile is deployed, other profiles using the same account are shown.
  • Standards. For definition requests, the standards document on the server is added to the pre-reading and to the checker.
  • Ordering a job alone. When a job is ordered alone from a flow, it is told that the predecessor's event is awaited.
  • Protection for weak models (from round 1):
  • If the request does not ask for a deletion, deleting an existing folder or profile and a deploy that drops existing jobs are rejected.
  • Only a database session that really blocks can be terminated.
  • The third of the same call is not run.
  • For commands that do not exist in the product, an example of the correct call is given.
  • Finish gate. It sends back at most twice. In requests that say "report without changing", it does not use red jobs as a reason.

The tuning was limited to one confirmation round (round 2, Usta only). Harmful went from 5 to 2, but most of the harm turned into false green (from 2 to 6). Correct went from 0 to 1. As instructed, the result was not chased; saha-donuk-2 was labelled as it stands. The hard hidden set (zor-test, 17 scenarios) was being run with gpt-oss under this label; when the report was written, 13 episodes had verdicts and neither rung had a correct one.

Limits and what was not measured

  • The hidden sets are open now. The test, hard test and catalogue test sets were hidden from the people developing the harness until the 16 November measurements. Since the repository was published they are open to everyone; later harness versions cannot present these sets as unseen. A new hidden set is needed.
  • Quota. The quota of all hosted models closed during the day: flash and hydrogen at about 13:00 (reopens on 21 November), argon at 13:36, sonnet at 15:19, gpt-oss at 15:20 (reopened in the evening). The strong-model data is the morning data of flash and hydrogen; after 21 November it will be completed with --atla. Argon and sonnet gave no usable result.
  • Restart and a single lane. At 15:42 the machine overheated and restarted (five lab copies and a second Ollama server with two slots). Since then the rule is one lab, one run, one model slot and a heat guard (tools/isi_bekcisi.py). The qwen3:14b hidden-test run is partial for this reason.
  • Windows. A Windows guest (lab/saha/windows: Windows Server 2022, WinRM, CtmAgent service) was set up, started and removed to free memory; it was never used. The live bench has no Windows server and no WinRM path.
  • Real Control-M. Not installed (the account has no download right). Measurements are on the Control-M-syntax layer over JS7.
  • Incidents by emulation. For incidents that cannot be produced in the lab, planned (docs/10), not done.
  • Catalogue sets (bench/saha/katalog-*). Not measured. The validation of the hidden half was left half done by a restart.
  • The scenario author's blindness. The author reported not having opened any of skills/, usta.py, tests/test_saha.py, opsbench.py, desk.py, checks.py, skills.py, docs/ilerleme.md and bench/saha/test/. A grep showed one unrelated line of usta.py; the file was not opened. A message sent to the wrong address did not cause a known leak.
  • Source reading. The party that wrote the harness read the list of SAB families and emulator faults for the coverage section; it did not change the harness according to them. The hard-set tuning was done with zor-dev evidence only.
  • Sample size. Scenario counts are small (10-30); no paired difference is statistically significant. Each episode was run once (pass^k was not measured).

SchedOps-Bench scenario catalogue

All 165 scenarios under bench/saha/, one table per set. Requests are English translations of the Turkish tickets, shortened to one or two sentences where the original is long; scenario ids are unchanged. The last column is a generated one-line summary of the checks the referee reads from the servers (job states, files, SQL results, definitions); long values are cut. Harm checks and the hidden root causes are left out here, see the scenario files. All account names, passwords and keys in the scenarios are lab-only fake values.

Family: fault = diagnose and repair a failed or stuck job, definition = create or change job definitions from a request, management = administrative request (move a job, rotate passwords, clean up). Job type follows the scenario field: AFT file transfer, EXC command or script, DBJ database, or mixed. See schedops-bench.md for how scenarios are judged.

Placeholders in checks: {GUN} is the scenario's date (YYYYMMDD).

Source files: bench/saha/<set>/*.json. The Turkish PDF catalogue with full details is docs/schedops-bench-senaryolar.pdf.
